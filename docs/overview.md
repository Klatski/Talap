## 0. Коротко

Мы сделали **среду**, а не агента. Она нужна, чтобы когда-нибудь дообучать ИИ-аудитора:

1. **Генератор** создаёт синтетическую компанию за один отчётный период: книгу проводок, счета,
   платежи и курсы валют. Внутрь он прячет 0–12 бухгалтерских ошибок четырёх типов и записывает
   правильный ответ (эталон) в закрытые файлы.
2. **Среда** даёт агенту узкий набор инструментов в стиле Gymnasium: листать таблицы, открывать
   записи и документы, считать на безопасном калькуляторе, отправлять выводы. Действий не больше 100,
   времени не больше 60 секунд.
3. **Оценщик** в отдельном процессе сопоставляет выводы агента с эталоном (взаимно однозначно, с
   доказательствами), считает P/R/F1 и награду по формуле ТЗ.

Всё работает только на стандартной библиотеке Python 3.11, без сети, GPU и сторонних пакетов, и
запускается одной командой `python check.py`.

**Ключевые числа**

| Что | Значение |
|---|---|
| Открытые эпизоды | 10 train + 10 dev + 1 заглушка; 4 чистые компании; 87 ошибок в train+dev |
| Размер эпизода | 234–1519 проводок, 65–153 документа, 0–12 ошибок; 5 базовых валют, 8 часовых поясов |
| Тесты | 302: генератор 79, среда 141, оценщик 78, карточка жюри 4 |
| Oracle | F1 = 1 и награда 1.0 на всех 21 открытом и 40 закрытых (имитация) эпизодах |
| Простая сверка (детектор лёгкости) | F1 0.21 — задача требует анализа доказательств |
| «Пометить всё» | 0 TP из 600 выводов, награда −1 на каждом эпизоде |
| Карточка жюри (имитация раздела 10 ТЗ) | 100/100: 20/20 + 20/20 + 20/20 + 20/20 + 10 |
| Чистый прогон с нуля | все 7 этапов PASS за ~135 с на 2 ядрах, 0 обращений к сети, память ≤ 181 МБ |
| Время одного эпизода | ≤ 1 с (лимит ТЗ 60 с) |

## 2. Архитектура

```
 генератор (A)   (seed, config, версия[, соль]) ─► public/  manifest, policy, ledger, invoices, payments, fx
                                                └► private/ truth.json, provenance.json, counterfactual/

 ┌─────────────────────────┐  JSON-lines  ┌──────────────────────────┐  JSON-lines  ┌─────────────────────────┐
 │ процесс агента          │ ───────────► │ python -m env.server     │ ───────────► │ python -m grader.service│
 │ политика + env.AuditEnv │ ◄─────────── │ только открытые записи,  │ ◄─────────── │ эталон, matcher,        │
 │ (нет эталона и путей)   │  obs/reward  │ действия, лимиты, таймер │ reward/info  │ награда, журнал         │
 └─────────────────────────┘              └──────────────────────────┘ (eval: 0, {})└─────────────────────────┘
```

* **Три процесса.** Агент общается только с процессом среды, а эталон есть только в процессе
  оценщика. Оценщик отдаёт среде шесть открытых файлов эпизода и после завершения возвращает награду.
  У агента нет канала к оценщику. Корень с эпизодами и соль задаёт обвязка при запуске, а не `reset`,
  поэтому агент не может подсунуть свою папку.
* **Протокол** — одна JSON-строка на запрос и ответ по stdin/stdout (`env/protocol.py`). Мусорная
  строка или строка больше 4 МБ получает ограниченную ошибку и не расходует шаг; EOF закрывает всё.
* **Два клиента** с одинаковым поведением: `env.AuditEnv` — официальный, с изоляцией процессов;
  `env.LocalAuditEnv` — всё в одном процессе, для тестов и отладки.

**Путь одного шага.** Политика вызывает `env.step(action)`. Клиент классифицирует действие тем же
кодом, что и ядро (`env/jsonsafe.py`), и отправляет его серверу. Ядро (`env/core.py`) списывает шаг,
разбирает и выполняет действие над открытыми записями и возвращает наблюдение
`{result, error, remaining_steps}`. На `submit` или исчерпании лимита ядро вызывает оценщика.
Оценщик валидирует ответ, сопоставляет его с эталоном, пишет запись в журнал и возвращает награду:
в режиме train — политике, в режимах closed и eval — только в журнал.

**Пример использования**

```python
from env import AuditEnv
from policies import make_policy

with AuditEnv() as env:                                   # поднимает процессы среды и оценщика
    obs, info = env.reset(seed=0, config={"split": "dev", "index": 1, "mode": "train"})
    policy = make_policy("auditor")
    policy.reset(obs, info)
    done = False
    while not done:
        obs, reward, terminated, truncated, info = env.step(policy.act(obs))
        done = terminated or truncated
    print(reward, info["f1"])
```

## 3. Данные эпизода

### 3.1. Файлы

```
episodes/<split>/<episode_id>/
  public/   manifest.json  policy.json  ledger.csv  invoices.jsonl  payments.jsonl  fx.csv
  private/  truth.json  provenance.json        ← только оценщик
  private/counterfactual/  те же 6 файлов без внесённых ошибок (для проверки данных)
episodes/<split>/index.json                     ← seed, конфиг, дайджест (открыто для train/dev)
```

| Файл | Содержимое | Ключ записи |
|---|---|---|
| `ledger.csv` | row_id, timestamp, account, debit_minor, credit_minor, currency, entity_id, invoice_id, payment_id | `row_id` (`L-XXXXXXXX`) |
| `invoices.jsonl` | doc_id, invoice_id, entity_id, issued_at, due_at, currency, total_minor, line_items[] | `invoice_id` (`INV-…`), документ `doc_id` (`D-…`) |
| `payments.jsonl` | doc_id, payment_id, timestamp, currency, amount_minor, invoice_refs | `payment_id` (`PAY-…`), документ `doc_id` |
| `fx.csv` | date, source_currency, target_currency, rate | `fx_id` = `FX:<src>:<dst>:<date>` (вычисляет среда) |
| `manifest.json` | schema_version, generator_version, episode_id, base_currency, currency_exponents, period_start/end, timezone, counts, rounding, tables | — |
| `policy.json` | пояс компании, границы периода, правило даты курса, округление, разнесение платежей, план счетов | — |

### 3.2. Правила значений

* Время — ISO-8601 с секундами и явным смещением. **Смещения у разных записей разные**, сравнивать
  можно только моменты времени.
* Деньги — целые числа в минимальных единицах. Разрядность берётся из `manifest.currency_exponents`:
  JPY 0, KWD 3, остальные 2.
* Курсы — десятичные строки. `rate` показывает, сколько базовой валюты дают за 1 иностранной. В
  `fx.csv` только рабочие дни.
* Отсутствующая ссылка — явный `null`, без угаданных связей. Книга ведётся только в базовой валюте.

### 3.3. Политика учёта (что такое «правильно»)

* Документ относится к периоду по своему времени, **переведённому в пояс компании**.
* Курс берётся на дату документа (`document_date`) или на предыдущий день (`previous_day`). Если на
  эту дату курса нет, используется последний более ранний.
* Конвертация: `base_minor = round(src_minor × rate × 10^(exp_base − exp_src))`, округление
  `half_up` или `half_even` по политике.
* Счёт проводится как Дт 1200 / Кт 4000. Платёж: Дт 1000, Кт 1200 по каждой ссылке (по курсу
  счёта), неразнесённое — на 2300, курсовая разница — на 7900. Возврат: Дт 2300 / Кт 1000.

### 3.4. Открытые сплиты

| Сплит | Конфиги (по эпизодам) | Ошибок |
|---|---|---|
| train | clean_small, clean_medium, two_types, all_types, fx_cutoff, interaction_payment, interaction_invoice, interactions_both, heavy, mixed_random | 0, 0, 2, 4, 4, 4, 4, 5, 12, 7 (= 42) |
| dev | clean_medium, clean_large, mixed_random, all_types, interaction_payment, interaction_invoice, interactions_both, heavy, mixed_random, two_types | 0, 0, 8, 4, 4, 4, 5, 12, 6, 2 (= 45) |

## 4. Генератор (зона A)

### 4.1. Конвейер: сначала история, потом документы, потом ошибки

```
config ─► Params (сэмплинг по seed)                               generator/config.py
      └─► History: курсы, клиенты, каталог, счета, граничные        generator/history.py
          документы, план оплат, платежи
      └─► проводки чистой истории ─► check_clean()                  generator/invariants.py
      └─► inject_all(): ошибки меняют только проводку документа     generator/inject.py
          или добавляют документ-дубль
      └─► проводки заново + фоновые расходы ─► check_after()
      └─► render(): ID и порядок строк назначаются ЗДЕСЬ             generator/render.py
      └─► audit(public) == truth и достаточность наборов            generator/audit.py
```

* У каждой стадии свой генератор случайных чисел
  `random.Random("<версия>|<seed>|<дайджест конфига>|<соль>|<попытка>|<стадия>")`.
* Документы-первоисточники (счета, платежи, курсы) никогда не портятся, портится только их проводка.
  Поэтому по открытым записям верный учёт всегда восстановим.
* Сумма ошибки берётся из фактических строк книги после перестроения проводок, а не считается отдельно.

### 4.2. Четыре типа ошибок

Допуск суммы во всех типах — 1 минимальная единица. Валюта должна совпадать точно.

| Тип | Что произошло | affected_ids | Сумма / валюта | Допустимые наборы доказательств |
|---|---|---|---|---|
| `duplicate_invoice` | Счёт введён повторно (тот же клиент, тот же момент, идентичные строки) и проведён второй раз | оба `invoice_id` | `total_minor` одного счёта, валюта счёта | `{doc_id A, doc_id B}` |
| `unapplied_payment` | Платёж по `invoice_refs` оплачивает счёт, но в книге кредит 1200 меньше или его нет, остаток лежит на 2300 | `{payment_id, invoice_id}` | сумма строки 2300, базовая валюта | `{doc_id платежа, row_id строки 2300}` |
| `fx_rate_error` | Сумма в книге посчитана не по курсу даты из политики | `{invoice_id}` или `{payment_id}` | \|проведено − верная конвертация\|, базовая валюта | `{doc_id, строка 1200 или 4000, FX верной даты}`; у платежа `{doc_id, строка 1000, FX}` |
| `cutoff_error` | Документ другого периода (по поясу компании) проведён в этом | `{invoice_id}` или `{payment_id}` | \|сумма документа\|, валюта документа | `{doc_id, любая строка проводки документа}` |

Внутри типов есть варианты (они записываются в `provenance`):
* курс: соседняя дата, чужое правило, дата оплаты, дата в смещении документа, дата по UTC;
* cut-off: тот же момент, сдвиг внутрь периода, неверно прочитанное смещение;
* распределение: полностью пропущено или частично.

### 4.3. Взаимодействующие ошибки (2 сценария)

Каждый сценарий даёт **две отдельные записи** в эталоне с общим `scenario_group`, и сумма каждой
считается по правилу своего типа.

* `fx_partial_boundary_payment`. Валютный платёж у границы периода, время записано в смещении, где
  дата «перескакивает» границу. Бухгалтер взял курс по записанной дате и разнёс платёж частично, отсюда
  `fx_rate_error` + `unapplied_payment`. Cut-off здесь нет: это ловушка для наивной сверки дат.
* `cutoff_fx_boundary_invoice`. Валютный счёт из соседнего периода, который по записи выглядит
  текущим, проведён в этом периоде по курсу записанной даты, отсюда `cutoff_error` + `fx_rate_error`.

### 4.4. Чистые компании и отвлекающие случаи

Есть полностью чистые компании (0 ошибок) и законные случаи, похожие на ошибки, которые в эталон не
попадают:
* повторяющиеся счета с той же суммой (новый `order_ref` каждую неделю);
* частичные отгрузки, разбитые, частичные и пакетные платежи;
* переплата с возвратом, платежи без ссылок (законно на 2300);
* документы у границы периода в «обманчивых» смещениях;
* задержка проводки внутри периода, курсы выходных.

Список отвлекающих случаев эпизода лежит в `provenance.distractors`, по нему разбираются FP.

### 4.5. Почему эталону можно верить

1. **Инварианты чистой истории** (до внесения ошибок):
   * сумма строк равна итогу счёта;
   * распределения не больше суммы платежа и итога счёта;
   * каждая проводка сбалансирована;
   * проведены ровно документы периода, все конвертации идут по политике.
2. **Независимая самопроверка** (`generator/audit.py` не импортирует генератор) по одним открытым
   файлам заново выводит все расхождения. Эпизод выпускается, только если выведенное совпадает с truth
   и каждый набор доказательств сам по себе воспроизводит тип и сумму.
3. **Контрфактическая чистая версия**: та же история и те же ID, но без ошибок. В ней audit не находит
   ничего, а разница с испорченной версией касается только документов из truth.
4. **Вторая независимая реализация** — наш аудитор (§7). Он написан по контракту, не видя кода
   генератора, и совпадает с эталоном на всех открытых эпизодах, на 50 новых конфигах и их парах.

### 4.6. Против утечек через артефакты

* ID случайные (`L-7Q2K…`) и назначаются после внесения ошибок. Нет префиксов вроде `dup_`, пропусков
  и последовательностей.
* Строки отсортированы по времени со случайным тай-брейком, внесённые строки не стоят в конце файла.
* Смещения времени разные у ~28% документов, задержка проводки есть у ~25% корректных документов.
* `python -m generator leakcheck` (наивный Байес по признакам формы записи) даёт AUC 0.54–0.55, это
  уровень случайного угадывания.

### 4.7. Преобразование «перестановка + смена ID»

`transform_texts / transform_episode` переставляют строки и меняют **все** ID, а truth и provenance
переотображаются. `remap_findings` переводит ответ на новые ID. На этом построены парные проверки:
ответ oracle и награды должны сохраниться.

### 4.8. Конфиг генератора

Все поля необязательны (`schemas/generator_config.schema.json`, пресеты — `generator/configs/*.json`):
* `size`: small / medium / large;
* `base_currency`, `foreign_currencies`, `timezone`, `period` (`YYYY-MM`);
* `rounding_mode`, `fx_rate_date_rule`;
* `errors.<type>`: число или `[lo, hi]`;
* `scenarios.<name>`, `distractors.<name>`.

Всего не больше 12 ошибок, сценарий считается за 2.

### 4.9. Закрытая проверка своими силами

* `python -m generator holdout --salt <секрет> --out <dir>` собирает 20 эпизодов как у жюри
  (5 чистых, 5 со взаимодействиями, 10 смешанных) на новых сочетаниях параметров: любой пояс
  −11:00..+13:00 с шагом 15 минут, любой месяц 2021–2034, все базовые валюты. Рядом пишутся 20 пар.
* `python -m generator stress --n 600` прогоняет 600 случайных конфигов со всеми проверками,
  результат 600/600.

## 5. Среда (зона B, `env/`)

### 5.1. reset

```python
obs, info = env.reset(seed, config)
```

Ключи `config`:
* `episode_dir` — каталог эпизода с любым именем, как его подаёт жюри (`{"mode": "closed", "episode_dir": …,
  "team_config": {…}}`). Каталог загружается как есть, без генерации и смены ID; раскладка `public/` +
  `private/` или плоская. Повторный reset начинает эпизод заново;
* `split` вместе с `episode_id`, или `index`, или ничем (тогда берётся `seed mod N`);
* либо `generator` / `team_config`: имя пресета или объект-конфиг (эпизод генерируется в процессе
  оценщика по seed и соли обвязки);
* `mode` (`train` / `eval` / `closed`), `max_steps` (1..100), `time_limit_s` (0..60], `config_version`.

Интерфейс жюри целиком (`generate_episode`, `make_env`, `score_episode`) — `judge_adapter.py` и README,
раздел «Интерфейс жюри».

**Первое наблюдение:** `task` (текст задачи), `episode_id`, `manifest`, `policy`, `tables` (размеры и
поля), `issue_types` (описание четырёх типов), `matching` (правила TP), `actions` (справка),
`action_format`, `limits`, `remaining_steps`, `env_version`. `info` = `{env_version, mode}`. Seed,
путей и сведений об эталоне нет.

### 5.2. Действия

Формат жюри — `{"name": "<действие>", "args": {...}}`; плоская форма `{"action": …, …}` — то же действие.

```json
{"name": "list_records", "args": {"table": "ledger", "cursor": null, "limit": 50}}
{"name": "get_record", "args": {"table": "invoices", "id": "INV-…"}}
{"name": "get_document", "args": {"doc_id": "D-…"}}
{"name": "calculator", "args": {"expression": "round_half_up(23208 * 516.3571 / 100)"}}
{"name": "submit", "args": {"findings": {"episode_id": "ep-…", "findings": [ … ]}}}
```

* **list_records**: таблицы `ledger`, `invoices`, `payments`, `fx`. Не больше 50 строк (если `limit`
  больше, отдаётся 50). Ответ — `{"records": [...], "next_cursor": null | строка}`, первый курсор `null`.
  Курсор имеет вид `<table>.<offset>.<tag>`, где tag — sha256 от (эпизод, таблица, смещение). Он
  детерминирован, привязан к таблице и эпизоду, подделать его нельзя.
* **get_record**: сам объект записи по ключу таблицы (`row_id`, `invoice_id`, `payment_id`, `fx_id`).
* **get_document**: сам документ (объект счёта или платежа) по `doc_id`. Бизнес-ID здесь не принимаются.
* **calculator**: собственный парсер без `eval`.
  * Допустимы только `+ - * / ( )`, десятичные литералы без экспоненты, `abs`, `round_half_up(x[, n])`,
    `round_half_even(x[, n])`.
  * Вычисления в Decimal с 34 знаками.
  * Пределы: ≤ 256 символов, ≤ 128 токенов, вложенность ≤ 32, |значение| < 1e30.
  * Ответ — десятичная строка (`"0.1+0.2"` → `"0.3"`). Код, имена, `**` и `1e999` отклоняются.
* **submit**: завершает эпизод, ответ `{"accepted": true}` без оценки правильности (подробнее в §6). При
  неверной структуре ответа — `result: null` и ограниченная ошибка `invalid_submission` с первой причиной.

Наблюдение каждого шага — ровно `{result, error, remaining_steps}`. Награда по ходу всегда 0, подсказок
о правильности нет.

### 5.3. Ошибки: фиксированный каталог, каждая расходует шаг

| Код | Когда |
|---|---|
| `invalid_action` | не объект, не JSON, NaN, целое длиннее 4300 цифр, смешанные ключи, глубокая вложенность |
| `action_too_large` | действие больше 256 КБ (у submit порог 1 МБ без текста explanation — там это неверная структура и −1) |
| `unknown_action` | действие не из пяти (shell, sql, read_file и т.п.) |
| `missing_argument` / `unexpected_argument` / `invalid_argument` | не те аргументы или типы |
| `unknown_table` / `invalid_limit` / `invalid_cursor` | неверная таблица, limit или курсор |
| `not_found` / `document_not_found` | нет такой записи или документа |
| `calculator_error` | выражение отклонено (с кодом причины) |
| `time_limit` | вышло время, действие не выполнено, эпизод усечён |
| `episode_over` | шаг после конца эпизода, повторный submit не учитывается |
| `not_reset` | step без reset |
| `internal_error` | непредвиденный дефект среды; шаг списан, текст исключения не раскрывается |
| `grader_unavailable` | оценщик упал при завершении; эпизод всё равно закрыт, награда 0 |

Тексты ошибок не содержат ввода агента, путей и сведений об эталоне. **Никакое исключение из `step`
наружу не выходит**: это проверено фаззингом на 3000 случайных действий и внедрением сбоев.

### 5.4. Лимиты и завершение

* Не больше **100 шагов, включая submit**. `submit` даёт `terminated=true`. Если последний
  разрешённый шаг прошёл без submit, получается `truncated=true` и пустой итоговый ответ.
* **60 секунд** на эпизод от `reset`, время политики входит. Когда время вышло, действие не выполняется:
  `truncated=true`, ошибка `time_limit`. Сторожевой таймер закрывает эпизод у оценщика, даже если агент
  молчит или завис.
* `reset` или `close` посреди эпизода записывается как `abandoned` (усечён, пустой ответ).
* **Любой submit завершает эпизод**, даже нечитаемый. Если нет аргумента `findings`, `args` не объект,
  ответ не JSON или больше 1 МБ (текст explanation в размер не входит), это неверная структура и −1.
  Прочие аргументы игнорируются. Причину среда передаёт оценщику отдельным полем, подделать её из ответа
  нельзя.

### 5.5. Режимы

* **train** — после завершения политика получает награду и в `info` агрегаты: `valid, errors, tp, fp,
  fn, precision, recall, f1, inspection_steps, truncated_reason, reward_experimental`.
* **closed** (имя жюри) и **eval** — политика всегда получает `0.0` и `{}`, включая завершение. Результат
  остаётся только в журнале оценщика. Строка эпизода (окружение, версии, seed, config, метрики, награда,
  разбор) дописывается сразу по его завершении. Так выполнено требование ТЗ: «награда и диагностика
  остаются у оценщика до конца прогона».

### 5.6. Изоляция, утечки, детерминизм

* **Песочница политики** (`env/sandbox.py`). Политика работает в отдельном ограниченном процессе:
  `python -I -S -B` в пустом временном каталоге, код политики приходит текстом, аудит-хук и на Linux
  seccomp закрывают файлы, процессы (fork и clone без `CLONE_THREAD` — на уровне ядра), сеть, ctypes и
  импорт оценщика; на Linux адресное пространство ограничено 1 ГиБ. Враждебная политика, знающая путь к
  `truth.json`, оттуда ничего не получает; без песочницы она же берёт 12/12 и 1.0 (негативный контроль,
  `tests/env/test_env_sandbox.py`). Зависшая политика ждётся не дольше 60 с эпизода.
* Тест изоляции прогоняет эпизод в отдельном процессе. В памяти агента нет ни одного объекта эталона,
  аудит-хуки не видят открытия закрытых файлов, отрицательный контроль срабатывает.
* Сканер утечек A проверяет все траектории: ID ошибок, сценарии, seed, скрытые суммы, закрытые пути.
* `reset` чистый: последовательность A → B → A даёт для A побайтово ту же траекторию, две загрузки не
  делят ни одного изменяемого объекта.
* Одинаковые seed + config + версия + действия дают побайтово одинаковые наблюдения и награды в любом
  процессе и при любом `PYTHONHASHSEED`.

## 6. Оценщик (зона B, `grader/`)

### 6.1. Формат ответа

```json
{"episode_id": "ep-…", "findings": [
  {"type": "fx_rate_error", "affected_ids": ["PAY-…"], "claimed_amount_minor": 1234, "currency": "KZT",
   "evidence_ids": ["D-…", "L-…", "FX:USD:KZT:2026-03-06"], "explanation": "коротко, почему"}]}
```

### 6.2. Структура и содержимое (точные соглашения matcher жюри)

**Неверная структура** (эпизод закрыт, награда −1, метрики `null`, ошибка в журнале):
* отсутствует обязательное поле;
* неверный тип значения: строка или bool вместо целой суммы, не список строк в `affected_ids` или
  `evidence_ids`, не строка в `type`, `currency`, `explanation`;
* больше 30 выводов, больше 10 `evidence_ids` (до удаления повторов);
* `explanation` длиннее 1000 Unicode code points;
* чужой `episode_id`.

**Неверное содержимое при верной структуре — просто FP:** неизвестный `type`, валюта в другом регистре
или с пробелом, отрицательная сумма, пустой `affected_ids`, несуществующий `evidence_id`.
Поля сверх формата игнорируются. Валидатор — зеркало `schemas/findings.schema.json`, согласие с ним
проверено фаззингом.

### 6.3. Сопоставление (`grader/matcher.py`)

* **Нормализация.** `affected_ids` и `evidence_ids` сравниваются как множества, так что порядок и
  повторы не важны. Строки сравниваются точно, без смены регистра и обрезки пробелов.
* **TP**, только если выполнены все условия:
  1. тот же `type`;
  2. то же множество `affected_ids`;
  3. та же валюта;
  4. |заявлено − эталон| ≤ τ (`amount_tolerance_minor`; без поля 0);
  5. все `evidence_ids` существуют в открытых данных эпизода (иначе FP, пример M04);
  6. `evidence_ids` содержат **хотя бы один допустимый набор целиком** (лишние существующие ID разрешены).
* **Паросочетание** максимальной мощности (алгоритм Куна), а не жадное. Среди максимальных выбирается
  лексикографически наименьшая последовательность пар (`issue_id`, индекс вывода): M10, M11. Порядок
  выводов не меняет TP/FP/FN и награду.
* Блок 3 правил жюри (20 тестов) и примеры M01–M12 проверяются дословно в
  `tests/grader/test_grader_jury_rules.py` через `judge_adapter.score_episode`.
* Несопоставленные и повторные выводы считаются FP, пропущенные ошибки — FN. Текст `explanation` в
  сопоставлении не участвует.

### 6.4. Метрики и награда (`grader/metrics.py`, точная арифметика `Fraction`)

```
P  = TP / (TP + FP)          (нулевой знаменатель -> 0)
R  = TP / (TP + FN)          (нулевой знаменатель -> 0)
F1 = 2TP / (2TP + FP + FN)   (пустой эталон и пустой ответ -> 1; пустой эталон и есть выводы -> 0)
reward = clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)
inspection_steps = все шаги, кроме submit (шаги с ошибкой тоже считаются)
```

* **Экспериментальная награда** (`reward_experimental`) — такая же, но усечённый эпизод получает −1.
  Она закрывает лазейку «молчать до лимита на чистой книге». Показывается отдельно и общую не заменяет.
* **Журнал оценщика** (JSONL) пишется на каждый эпизод: режим, причина конца, валидность, TP/FP/FN,
  P/R/F1, награды, диагностика. Диагностика включает причины FP (`wrong_amount`, `duplicate`,
  `no_such_issue`…), FP на отвлекающих случаях и FN «почти попал». Политика её не видит никогда.

### 6.5. Пример, посчитанный вручную

На заглушке 6 ошибок. Ответ: два верных вывода и курсовой с суммой больше на 2 при допуске 1; перед
submit 3 шага исследования. Получается TP 2, FP 1, FN 4, F1 = 4/(4+1+4) = 4/9, награда
= 8/9 − 1 − 0.006 = **−527/4500 ≈ −0.1171**. Ровно это и выдаёт программа: через изолированные
процессы, в train и в журнале eval (`tests/grader/test_grader_handworked.py`).

## 7. Политики (`policies/`)

Интерфейс один для всех, это и есть «адаптер базовой политики»:

```python
class Policy:
    name: str
    def reset(self, observation: dict, info: dict) -> None: ...
    def act(self, observation: dict) -> dict: ...          # одно действие из §5.2
```

Создание: `policies.make_policy(name, seed=0, truth=None)`.

| Политика | Что делает | Зачем |
|---|---|---|
| `random` | Случайные шаги с фиксированным seed: смесь верных и заведомо неверных действий (чужие таблицы и ID, испорченные курсоры, опасные выражения), иногда превышение лимита, затем случайный submit (иногда кривой) | Проверяет контракт, ошибки, лимиты и воспроизводимость |
| `reconcile` | «Простая сверка по поверхности»: даты как записаны (без поясов), курс на записанную дату (без `previous_day` и правила округления), дубль = два счёта клиента с той же суммой, любой кредит 2300 = неразнесённый | Детектор лёгкости и утечек: если она находит ошибки, генератор выдаёт их по артефактам |
| `flag_all` | До 30 выводов: каждый документ × тип, сумма = сумма документа | Атака: обязана получать плохую награду |
| `oracle` (A) | Отправляет эталон с полными наборами доказательств; создаётся только обвязкой на стороне оценщика | Проверяет, что максимум награды достижим (1.0) |
| `auditor` (B, демо) | Читает все таблицы через инструменты (≤ ~41 шага) и по контракту заново выводит все расхождения с минимальными доказательствами | Демо «умной» политики и независимый валидатор данных A |

### 8.3. Карточка жюри (`tests/jury/scorecard.py`)

Раздел 10 ТЗ, переведённый в код один в один и прогнанный на 20 закрытых эпизодах имитации.

* **Контракт и изоляция, 20 проверок (C01–C20):**
  * поля reset и форма step;
  * отсутствие seed и путей;
  * пагинация и курсоры, точность записей;
  * калькулятор (точность и отказ на коде);
  * неизвестные действия и ID, мусорный ввод;
  * submit, 100 шагов, тайм-аут, поведение после конца;
  * нулевая награда по ходу, eval, неверная структура;
  * сканер утечек, A → B → A.
* **Данные и эталон, 20 эпизодов:**
  * бухгалтерские равенства до внесения ошибок;
  * независимый вывод после внесения совпадает с эталоном;
  * каждое доказательство есть в открытых данных;
  * размеры в пределах ТЗ.
* **Надёжность награды, 20 проверок (R01–R20):**
  * oracle = 1, порядок не важен, ID как множества;
  * дубли, «один вывод на две ошибки», нежадное сопоставление;
  * чистые книги, ложные обвинения, «пометить всё»;
  * угаданные ID, поддельные и неполные доказательства, чужая валюта;
  * граница допуска, неверный тип, стоимость шагов, структура, независимость от текста;
  * все атаки A.
* **Воспроизводимость, 20 пар:**
  * повтор seed и действий в двух процессах;
  * пересборка побайтово;
  * эталон пары = переименованный эталон;
  * переименованный ответ oracle = 1.0;
  * награды 4 политик равны.

Результат: **100/100** (`reports/jury_scorecard.md`). Это имитация: seed жюри неизвестны.

### 8.4. Проверка самих проверок

* **Мутационные тесты.** В оценщик вносятся типичные баги:
  * игнор валюты;
  * схлопывание дублей;
  * бесплатные шаги;
  * игнор доказательств;
  * бонус за текст;
  * мягкая валидация.
  
  Отдельно портятся эталон и пара. Каждый раз падает именно та проверка, которая должна.
* **Ручные примеры** (`python tests/grader/test_grader_handworked.py --show`): 9 примеров и 7 неверных
  структур, ожидания выведены руками по формулам ТЗ. Свой пример можно проверить так:
  `python -m grader --truth T.json --submission S.json --steps N`.
* **Снимки (golden).** Результаты по каждому эпизоду сравниваются с закоммиченными отчётами (без
  времени). Любое изменение поведения видно сразу.

### 8.5. Чистое окружение и CI

* `python tools/clean_run.py` повторяет всю проверку с нуля:
  * свежий клон с GitHub в путь с пробелом;
  * новый venv без pip;
  * урезанное окружение и пустой TEMP;
  * 2 ядра на все процессы;
  * сеть запрещена audit-хуком;
  * замер памяти.
  
  Последний прогон: 7/7 PASS за 135 с, 107 процессов, 0 попыток сети, ≤ 181 МБ, репозиторий не изменён,
  мусора нет.
* **CI** (`.github/workflows/check.yml`) на каждый push запускает `python check.py` на Linux и
  `docker run --network none --cpus 2 --memory 4g`, это ровно лимиты ТЗ, плюс демо в контейнере.

## 12. Ключевые решения и почему

| Решение | Почему |
|---|---|
| Три процесса (агент / среда / оценщик) | Эталон физически недоступен агенту; утечка блокирует оценивание |
| Сначала история, потом документы, потом ошибки | Эталон описывает реальное причинное изменение, а не «подозрительную строку»; верный учёт всегда восстановим |
| Самопроверка генератора + независимый аудитор B | Две реализации по одному контракту: если они расходятся, ошибка в данных или контракте |
| ID назначаются после внесения ошибок, порядок перемешан | Ошибку нельзя найти по позиции, префиксу или пропуску в нумерации |
| Максимальное паросочетание, а не жадное | Жадный выбор недосчитывает TP, когда один вывод подходит к двум ошибкам |
| Доказательство — только `doc_id` / `row_id` / `fx_id`, набор целиком | Однозначно и проверяемо; лишние ID разрешены, угадать набор без анализа нельзя |
| Награда в `Fraction` | Точная арифметика: никаких 0.30000000000000004 и расхождений между машинами |
| Любой submit завершает эпизод | Нельзя «прощупывать» оценщик кривыми ответами без последствий |
| Строгая структура: лишнее поле → −1 | Так понято «неверная структура» в ТЗ; правило едино и описано в схеме |
| Общая награда по ТЗ неизменна, экспериментальная отдельно | ТЗ требует сохранить общую; лазейку «молчать до лимита» показываем отдельно |
| Ошибки из фиксированного каталога без эха ввода | Через ошибки ничего не утекает, тексты стабильны и детерминированы |
| Только stdlib | Ноль проблем с установкой у жюри и в контейнере без сети |

## 13. Честные ограничения

* **Лазейка общей награды.** На чистой книге «молчать до лимита» даёт 0.8. Формулу ТЗ мы не меняем,
  экспериментальная награда (усечение → −1) показана отдельно.
* **Строгие наборы доказательств.** `INV-…` вместо `D-…` не засчитывается.
* **Ядерная граница песочницы — только на Linux** (seccomp). На Windows и macOS работает аудит-хук: он
  закрывает чтение, процессы, сеть и импорт оценщика, но `os.stat` по известному пути вернёт метаданные
  файла (не содержимое). Для закрытого прогона нужен Linux-контейнер; ветку seccomp проверяет CI.
  Запрет `_imp.create_builtin` для запрещённых модулей — защита в глубину внутри процесса, не граница:
  на Linux её дублирует ядро (нет exec, fork, сокетов), на Windows граница мягкая.
* **Допуск суммы τ = 1 у курсовой разницы** (округление пересчёта по курсу). У остальных типов τ = 0,
  как по умолчанию в правилах жюри.
* **Тайм-аут по реальному времени.** На очень медленной машине эпизод может оборваться раньше.
* **Упрощённый учёт.** Только дебиторка, книга в базовой валюте, без НДС и начальных остатков. Курсы
  синтетические.
* **Награда не доказывает пригодность для реального аудита.** Модель не обучалась, есть только
  скриптовые политики.
* **Наши пороги.** Простая сверка — наш вариант «простого алгоритма», пороги детекторов утечек выбраны
  нами.
* **Карточка жюри — имитация.** 100/100 на нашей соли — необходимое, но не достаточное условие.
* **Docker не запускался локально.** Его проверяет CI на Linux.

## 14. Словарь

| Термин | Значение |
|---|---|
| Эпизод | Одна компания за один отчётный период: открытые файлы и закрытый эталон |
| Эталон (truth) | Список настоящих ошибок с суммами и допустимыми наборами доказательств |
| Provenance | История генерации: seed, конфиг, проверки, причина и вариант каждой ошибки, отвлекающие случаи |
| Контрфакт | Та же компания без внесённых ошибок, для проверки данных |
| Отвлекающий случай | Законная ситуация, похожая на ошибку (повторный счёт, разбитый платёж…) |
| Набор доказательств | Минимальный набор записей, по которому восстанавливаются тип и сумма ошибки |
| TP / FP / FN | Верный вывод / лишний или повторный / пропущенная ошибка |
| inspection_steps | Шаги исследования: все, кроме submit |
| train / eval | Награда видна политике / награда только у оценщика |
| Пара | Тот же эпизод после перестановки строк и смены всех ID |
| Holdout | Закрытые эпизоды на секретной соли и новых сочетаниях параметров |
| Oracle | Политика, которая знает эталон; проверяет, что максимум награды достижим |
| Снимок (golden) | Закоммиченный отчёт, с которым сравнивается каждый прогон |

# Записка о дизайне: RL-среда для ИИ-аудитора

Среда для возможного дообучения модели финансового аудита. Генератор создаёт синтетическую
компанию за один отчётный период со скрытыми ошибками. Агент расследует её через узкий набор
инструментов и отправляет выводы с доказательствами, оценщик считает награду. Модель здесь не
обучается: среда даёт воспроизводимые взаимодействия, траектории и оценку качества.

## 1. Устройство

```
 генератор (A)  (seed, config, версия[, соль]) ─► public/  manifest, policy, ledger, invoices, payments, fx
                                               └► private/ truth.json, provenance.json, counterfactual/
 ┌───────────────────────────┐ наблюдения  ┌───────────────────────────┐
 │ политика: env/sandbox.py  │ ◄────────── │ обвязка или жюри          │  judge_adapter.py: generate_episode,
 │ отдельный процесс -I -S -B│ ──────────► │ env.AuditEnv: reset/step; │  make_env, score_episode;
 │ пустой каталог, код из    │  действия   │ пути, seed, config        │  пути, seed и config есть только здесь
 │ памяти, аудит-хук+seccomp │             └─────────────┬─────────────┘
 └───────────────────────────┘                JSON-lines │ reset / step
                                           ┌─────────────▼─────────────┐  JSON-lines  ┌─────────────────────────┐
                                           │ python -m env.server      │ ───────────► │ python -m grader.service│
                                           │ только открытые записи,   │ ◄─────────── │ эталон, matcher,        │
                                           │ действия, лимиты, таймер  │ reward/info  │ награда, журнал         │
                                           └───────────────────────────┘ closed: 0, {}└─────────────────────────┘
```

* **Изоляция** (раздел «Граница доступа» правил жюри).
  - Эталон живёт только в процессе оценщика. Процессу среды оценщик отдаёт шесть открытых файлов, а после
    submit возвращает награду (в `closed`/`eval` — ноль).
  - Политика работает в **отдельном ограниченном процессе** (`env/sandbox.py`, `judge_adapter.load_policy`).
    Это `python -I -S -B` в пустом временном каталоге с очищенным окружением; путей к репозиторию и эпизоду
    процесс не знает. Код политики приходит текстом и грузится из памяти.
  - До первой строки политики ставятся необратимые ограничения: аудит-хук (`open`, листинг каталогов,
    процессы, сеть, `ctypes`, байт-код, субинтерпретаторы, импорт `grader`/`generator`/`env` →
    `PermissionError`) и на Linux seccomp-фильтр ядра (открытие и `stat` файлов по пути, exec, сокеты,
    ptrace, сигналы → `EPERM`). Политика получает только наблюдения и результат `step`.
  - `reset` вызывает обвязка, поэтому политика не может подсунуть оценщику свою папку.
  - Проверено:
    - `test_env_sandbox`: враждебная политика знает точный путь к `truth.json` эпизода с 12 ошибками и
      пробует около 20 способов (файлы, процессы, импорт оценщика, gc, ctypes, сеть, `/proc`, сигнал
      чужому процессу). Из песочницы она не получает ничего: награда −1, процесс-жертва жив. Та же политика
      в процессе обвязки (негативный контроль) читает эталон и получает 12/12 и 1.0.
    - `test_env_isolation`: в памяти процесса агента нет ни одного объекта эталона.
* **Контракт** (`docs/contract.md`, разделы 7–9, и README «Интерфейс жюри»).
  - `reset(seed, config) -> (obs, info)` и `step(action) -> (obs, reward, terminated, truncated, info)`
    в стиле Gymnasium, JSON-совместимые.
  - Действие — конверт жюри `{"name", "args"}`, плоская форма — синоним. Действия: `list_records`
    (`{records, next_cursor}`, ≤ 50 строк, стабильные подписанные курсоры), `get_record` и `get_document`
    (сам объект), `calculator` (собственный парсер, Decimal, без eval, десятичная строка) и `submit`
    (`{"accepted": true}`).
  - `mode: "closed"` с `episode_dir` грузит ровно переданный каталог любого имени: так жюри подаёт свои
    копии для парных проверок. `train` с `team_config` генерирует эпизод генератором команды.
  - Ошибки берутся из фиксированного каталога без эха ввода, каждая расходует шаг.
  - Лимит — 100 шагов вместе с submit и 60 с на эпизод, время политики входит. Сторожевой таймер
    закрывает эпизод у оценщика, даже если политика молчит или зависла.
  - Наблюдение шага содержит ровно `{result, error, remaining_steps}`.
  - Любой submit завершает эпизод. Если его нельзя прочитать (нет `findings`, не JSON, больше любого
    валидного ответа), это неверная структура (−1).
  Враждебный ввод (глубокая вложенность, целые длиннее 4300 цифр, NaN, смешанные ключи) не роняет
  `step` и даёт одинаковый итог в изолированной и внутрипроцессной среде (`test_env_hostile_input`).
  Дефект самой среды даёт ограниченную ошибку `internal_error`, падение оценщика при завершении даёт
  `grader_unavailable`. Исключение из `step` наружу не выходит (`test_env_fault_tolerance`, с фаззингом).
  `reset` чистый: A → B → A с тем же экземпляром политики даёт для A побайтово ту же траекторию, а две
  загрузки эпизода не делят ни одного изменяемого объекта (`test_env_reset_purity`).
* **Режимы.** В `train` терминальная награда и агрегированные метрики возвращаются политике. В `closed`
  (он же `eval`) политика всегда получает `0.0` и `{}`, включая завершение. Результат лежит в журнале
  оценщика: строка дописывается сразу по завершении эпизода, в ней окружение, версии, seed и config.
  Раннер проверяет, что в `closed` политика не увидела ненулевой награды.
* **Оценщик** (точные соглашения matcher жюри).
  - Сначала структура, она сверена со схемой фаззингом на 3000 ответах. Неверный тип значения,
    отсутствующее поле, больше 30 выводов, больше 10 доказательств или explanation длиннее 1000 code
    points дают −1 всему submit. Поля сверх формата игнорируются.
  - Структурно правильный вывод с неверным содержимым — просто FP. Это неизвестный тип, валюта в другом
    регистре, отрицательная сумма, несуществующий `evidence_id` (M04).
  - Чужой `episode_id` (строка) — не ошибка структуры по п. 8 жюри: ответ оценивается против текущего
    эпизода, несовпадение — предупреждение в журнале. Ответ другого эпизода TP всё равно не даёт: ID разные.
  - Ключ курса жюри `<date>:<src>:<dst>` приводится к `fx_id` и в выводе, и в наборах эталона.
  - Затем максимальное паросочетание (алгоритм Куна, не жадное). Ничьи разрешаются лексикографически
    наименьшей последовательностью пар (`issue_id`, индекс вывода), M10/M11.
  - TP требует всех условий: тип, множество `affected_ids`, валюта, сумма в допуске и полный набор
    существующих доказательств.
  - Блок 3 жюри (20 тестов) и примеры M01–M12 проверяются дословно через `score_episode` на фикстуре
    из определений (`test_grader_jury_rules`).
  - Награда считается в `Fraction` и только потом переводится в float:
  `clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`. `inspection_steps` — все шаги без submit,
  ошибочные тоже. Экспериментальная награда (усечение → −1) хранится отдельно и общую не заменяет.
* **Генератор** (`docs/generator.md`). Сначала скрытая история, потом документы, потом ошибки с
  записанной причиной. Самопроверка `audit(public) == truth`, контрфактическая чистая версия, ID
  назначаются после внесения ошибок, проверка утечек через артефакты. Каждый набор доказательств сам
  определяет тип, `affected_ids` и сумму: у платежа на несколько счетов в нём всё разнесение (строки 1200,
  счета, курсы), иначе недоразнесённый счёт по набору не установить.

## 2. Почему эталону можно верить: две независимые реализации
Аудитор B (`policies/auditor.py`) не импортирует генератор и написан по опубликованному контракту.
Он читает все таблицы через инструменты среды (≤ 41 шага) и заново выводит расхождения вместе с
доказательствами. Результат совпадает с эталоном A (F1 = 1, ни одного FP и FN) на всех 21 открытом
эпизоде, на 50 эпизодах с новыми сочетаниями параметров (10 чистых, 15 со взаимодействиями, 25
смешанных) и на их парах после перестановки и смены ID. На контрфактических чистых версиях он ничего
не находит. В ходе этой проверки нашлась одна ошибка: неверное ожидание в генераторе атак A для
сценария, где обе ошибки относятся к одному счёту (`docs/contract.md`, решение 5).

## 3. Измерения (`python check.py`, отчёты в `reports/`)
Train + dev, 20 эпизодов, режим eval, изолированные процессы (`reports/baselines.md`):

| политика | F1 (ср.) | micro F1 | возврат | возврат на чистых | шагов | время, с (ср./макс.) |
|---|---|---|---|---|---|---|
| oracle | 1.000 | 1.000 | 1.000 | 1.000 | 1.0 | 0.07 / 0.28 |
| auditor (демо) | 1.000 | 1.000 | 0.955 | 0.957 | 23.4 | 0.16 / 0.31 |
| reconcile (простая сверка) | 0.207 | 0.201 | −0.622 | −1.000 | 23.4 | 0.33 / 0.98 |
| random (seed 0) | 0.100 | 0.000 | −0.816 | −0.078 | 55.0 | 0.20 / 0.56 |
| flag_all | 0.000 | 0.000 | −1.000 | −1.000 | 4.2 | 0.08 / 0.25 |

Имитация закрытого прогона (`reports/holdout.md`): 20 эпизодов с солью на новых сочетаниях
параметров (5 чистых, 5 со взаимодействиями, 10 смешанных) и 20 пар. Oracle получает 1.0 на всех 40.
Награды oracle, аудитора, сверки и flag-all совпадают в каждой из 20 пар. Random совпадает в 18 из 20:
это ожидаемо, его действия зависят от `episode_id`, а тот меняется при смене ID.

**Разбор сбоев (с числами, train + dev).**
* Простая сверка даёт 53 TP и 388 FP. Из FP 120 приходятся на корректные документы у границы
  периода в «обманчивых» смещениях, 80 на законные повторяющиеся счета, 67 на задержку проводки,
  28 на разбитые платежи. Пропуски: 16 курсовых ошибок (не учтено правило `previous_day` или пояс
  компании), 9 cut-off, 9 неразнесённых платежей. Поверхностные признаки ошибок не выдают: средний
  F1 0.21. Тест-детектор требует F1 < 0.5 и точность < 0.3.
* «Пометить всё» (30 выводов на эпизод): 0 TP из 600, награда −1 на каждом эпизоде, в том числе на
  чистых.
* Random: 3 усечения по лимиту шагов, 3 неверные структуры (−1), ни одного TP. Его единственный
  положительный возврат — пустой ответ на чистой книге.
* Свойства награды из ТЗ проверены на всех 21 эпизоде (`test_grader_reward_properties`). Полный ответ
  лучше молчания. Молчание (1.0) лучше любого ложного обвинения на чистых книгах (−1). Дубли строго
  ухудшают награду. Разница между 0 и 99 шагами при равных ответах не больше 0.198. Чужая валюта,
  угаданные ID, неполные или поддельные доказательства и ответ другого эпизода не дают TP.
  Все 36 атак A × 21 эпизод (756 случаев) совпадают с ожиданием по ТЗ.

## 4. Воспроизводимость
Только локальные RNG, JSON с `sort_keys`, курсоры — sha256 от (эпизод, таблица, смещение), награда
считается в `Fraction`. В наблюдениях и траекториях нет времени, путей и seed. Тест запускает
раннер в трёх процессах с разными `PYTHONHASHSEED`, один раз в режиме «всё в одном процессе»:
файлы траекторий совпадают побайтово. `trajectories/trajectories.jsonl` (950 строк: random,
reconcile, flag_all, auditor на train) пересобирается в `check.py` и сравнивается с файлом в
репозитории байт в байт. Результаты базовых политик по каждому эпизоду (награда, P/R/F1, TP/FP/FN,
шаги, причины FP; без времени) сравниваются со снимками `reports/baselines.json` (100 прогонов) и
`reports/holdout.json` (200 прогонов на закрытой имитации). Любое расхождение даёт FAIL.

**Карточка жюри** (`tests/jury/scorecard.py`, этап 7 `check.py`, `reports/jury_scorecard.md`) переводит
раздел 10 ТЗ в код один в один. На 20 закрытых эпизодах имитации считаются 20 проверок контракта,
20 эпизодов (равенства до внесения ошибки, независимый вывод расхождений, доказательства есть в
открытых данных), 20 проверок награды и 20 парных проверок (повтор seed и действий в двух процессах,
пересборка побайтово, эталон пары = переименованный эталон, награды равны). Баллы считаются по
формуле жюри. Карточка сама проверена мутациями (`test_jury_sensitivity`): если в оценщик внести
типичный дефект (игнор валюты, схлопывание дублей, бесплатные шаги, игнор доказательств, бонус за
текст, мягкая валидация) или испортить эталон либо пару, падает нужная проверка.

**Определения проверок жюри (21.11)** проверяются в коде через тот же `judge_adapter.py`, который вызывает жюри:
* блок 1 (C01–C20) и парные проверки блока 4 — `tests/env/test_env_jury_adapter.py`. Преобразование в
  них своё, независимое от `generator/transform.py`: перестановка строк, ID в другом формате (`row/00012`,
  `doc:00007`, `bill.0042`), правка truth и provenance в копии. Награды oracle до и после совпадают, а со
  старыми ID или без доказательств TP нет;
* блок 3 (20 тестов) и M01–M12 дословно — `tests/grader/test_grader_jury_rules.py`;
* граница доступа — `tests/env/test_env_sandbox.py`.

Всё это входит в этап 2 `check.py`.

## 5. Честные ограничения
* **Лазейка общей награды.** На чистой книге пустой итоговый ответ даёт F1 = 1, поэтому «тянуть до
  лимита» приносит 0.8 по общей награде. Общую награду по ТЗ мы не меняем. Экспериментальная
  (усечение → −1) показывается отдельно в журнале и отчётах.
* **Наборы доказательств строгие.** Принимаются только `doc_id`, `row_id` и `fx_id`, бизнес-ID
  (`INV-…`) синонимами не считаются. Агент, сославшийся на счёт вместо документа, получит FP. Формат
  описан в первом наблюдении.
* **Ядерная граница песочницы — только на Linux.**
  - На Linux процесс политики закрыт seccomp-фильтром ядра и аудит-хуком. Ядро запрещает и новые процессы
    (`fork`, `clone` без `CLONE_THREAD`, `clone3` → `ENOSYS`), и смену лимитов; адресное пространство —
    1 ГиБ (`RLIMIT_AS`), core-файлов нет.
  - Модули, созданные мимо импорта (`_imp.create_builtin` / `create_dynamic`), отказывают запрещённым
    именам. Это защита в глубину внутри процесса Python (обёртку можно разобрать интроспекцией), а
    настоящую границу на Linux держит ядро.
  - На Windows и macOS работает только аудит-хук. Он отбивает все способы чтения файлов, запуска
    процессов, сети и импорта оценщика, но `os.stat` по заранее известному пути вернёт метаданные файла
    (размер, время) без содержимого.
  - Путей политика не знает: каталог эпизода ей не передаётся, рабочая директория — пустой временный
    каталог. Для закрытого прогона нужен Linux-контейнер (`Dockerfile`, CI).
  - Локально seccomp не проверялся: на машине разработки нет Linux. Ветку seccomp проверяет CI
    (`test_env_sandbox` ждёт там `seccomp: active`, пустой список сработавших способов, а
    `KernelLimits` — `EPERM` на fork, работающий поток, неизменный лимит и `MemoryError` на 2 ГиБ).
  - Если жюри запускает свою политику в своём процессе, а не через `judge_adapter.load_policy`, граница
    держится только на процессах среды и оценщика. Открытые train/dev лежат в репозитории вместе
    с эталоном: это открытые данные.
* **Допуск суммы τ = 1 у курсовой разницы** (остальные типы — τ = 0, как по умолчанию у жюри).
  Это документированное округление пересчёта по курсу (`policy.json`), опубликовано в контракте, раздел 4.
  Фикстуры жюри задают τ явно; `truth.json` без поля даёт τ = 0.
* **Тайм-аут измеряется по реальному времени.** На очень медленной машине последовательность шагов
  может оборваться раньше. Награда и траектории детерминированы, пока лимит не достигнут.
* **Учёт упрощён** (см. `docs/generator.md`): только дебиторка, книга в базовой валюте, без НДС и
  начальных остатков. Курсы синтетические.
* **Награда не доказывает пригодность для реального аудита.** Высокая награда означает лишь
  совпадение с нашим формальным эталоном. Мы не заявляем об улучшении какой-либо модели: обучения
  нет, есть только скриптовые политики.
* **Простая сверка — наш вариант** «простого алгоритма», а порог детектора утечек (F1 < 0.5) — наш
  выбор. У жюри может быть другая сверка.
* **Карточка жюри — имитация.** 100/100 на нашей соли — необходимое, но не достаточное условие: seed
  и сочетания параметров жюри неизвестны, а блок «инженерия» лишь проверяет, что нужные артефакты на
  месте. Оценку 0/1/2 за него ставит жюри.
* **Docker локально не запускался** (на машине разработки нет Docker). Сборку и запуск
  `docker run --network none --cpus 2 --memory 4g` на Linux выполняет CI (`.github/workflows/check.yml`).
  Команда в контейнере та же, `python check.py`, без сторонних зависимостей.
